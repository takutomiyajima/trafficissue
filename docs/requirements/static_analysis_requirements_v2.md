# Androidアプリ三者照合・構成説明支援システム 要件定義書 v2.0

作成日：2026年10月25日  
対象研究：開発要求・AIの実装説明・APK構成の照合によるAndroidアプリ開発支援  
状態：研究用システムの提案要件。現行実装の完成・性能・対応範囲を保証する文書ではない。  
基礎資料：2026年10月20日「開発意図照合システム プログラム仕様書 v1.0」および今回の研究方針。旧仕様は保存し、本書を新方針に対する要件の基準とする。詳細なAPI・JSON Schema・画面設計は、本書を基に別途定める。

## 1. 目的と成功条件

AIにAndroidアプリの開発を依頼した人が、要求とAIの説明だけでは把握しづらい通信・権限・外部SDKの構成を確認できるようにする。開発要求、AIが提示した実装説明、APKの静的解析で得られた証拠を対応付け、要求への適合、説明の裏付け、矛盾、説明漏れ候補、未指定・未確認事項を根拠付きで提示する。

研究上の成功は「AIの誤りが多数見つかること」ではなく、対象範囲内の照合を正確かつ再現可能に行い、判断できる範囲とできない範囲を明示できることである。非専門家にも読める表現は設計目標とするが、利用者実験なしで理解向上・時間短縮を実証したとはしない。本書は新規性を保証するものではない。

| ID | 研究上の問い | システムが提供する評価材料 |
|---|---|---|
| RQ1 | AIの実装説明は対象構成をどの程度説明しているか | 構成ごとの説明対応、説明資料の範囲、説明漏れ候補 |
| RQ2 | 要求不一致・説明矛盾・未確認を正しく識別できるか | 規則別の判定、証拠、失敗・判定不能の記録 |
| RQ3 | 三者の対応付けで確認事項の提示をどの程度改善できるか | 同じ情報を用いた基準表示と提案表示、正解表との比較用出力 |

## 2. 現状と前提

利用者から確認されている到達点は、(1)次のプロンプトによる旅行記録アプリの実装、(2)静的解析システムの基盤作成、の二点である。

> 写真と文章で旅行の記録を残し、過去の記録を検索できるAndroidアプリを作成してください。必要な構成を提案したうえで、実装してください。Android Studioでビルドできるプロジェクトとして出力してください。

本作業では現行コードと生成アプリの実体を監査していない。APKのビルド成否、解析JSONの現行形式、証拠位置の取得可否、SDK検出能力、API検出能力は未確認とする。旧仕様書内の実装状況は過去時点の情報として扱い、現行の能力とみなさない。

この要求は外部通信・位置情報・SDKを禁止していない。これらの存在だけで要求違反とはしない。旅行記録アプリは予備実験に用い、そこで定義や規則を変更した場合は、固定後の本評価と分離する。

## 3. 利用者、対象範囲、対象外

主利用者はAIに開発を依頼する開発者・開発依頼者。研究者は原文を構造化し、独立した正解表を作成する。初版ではローカルCLIと日本語Markdownレポートを基本とし、GUIとLLMの導入は必須としない。

| 区分 | 初版の範囲 |
|---|---|
| アプリ入力 | 単体APK、またはAPKとの対応が記録された既存静的解析JSON |
| 権限 | Manifest内の権限要求宣言。実際の付与・取得と区別 |
| 通信関連 | 埋め込みHTTP(S) URLの候補と発見位置。実通信先と区別 |
| SDK | 固定した検出台帳で対応する既知SDKの同梱証拠・候補 |
| 照合 | 人が確認して構造化した要求・AIの説明と、抽出した証拠との対応 |
| 説明 | 構成の意味、原文との関係、根拠、追加確認事項、判定限界 |
| 評価用ソース | 人手による正解確認で使用。自動判定へは混入させない |

対象外：実際の通信発生・送信内容・情報漏えいの確定、全データフローの復元、全機能・脆弱性の診断、暗号の総合評価、要求全文の完全な自動理解、AIの隠蔽意図や設計理由の推測、修正の自動実行。AAB・分割APK・動的ロードコード・難読化等は対応状況を明示し、未対応部分を確認済みとしない。

位置情報権限とURLの共存だけから、両者を結ぶ送信経路を作らない。SDKの一般的用途と、対象アプリで確認した用途を分ける。取得・保存・送信に関する説明が対象範囲を超える場合は、原文を残し「対象外」とする。

## 4. 利用フロー

1. 要求、生成時のAI回答、生成物、生成条件を保存し、ケースIDを付ける。
2. 要求とAIの実装説明を、人が対象項目へ構造化して確認する。
3. APKを静的解析する、または既存JSONを取り込む。
4. 抽出段階ごとの成功・失敗・範囲と、証拠の識別情報を確定する。
5. 構造化した要求・説明と証拠を照合する。
6. 説明が対応しない評価対象の構成を探し、説明漏れ候補を生成する。
7. レポートを出力し、必要に応じて人が確認記録を追加する。
8. 自動結果と独立正解を比較し、研究指標を集計する。

要求や説明の修正は元データを上書きせず版を更新する。生成時回答と、後から追加依頼した説明は種類を分ける。別バージョンのAPKに対する説明を同じ説明として流用しない。

## 5. 入力要件

| ID | 入力 | 必須性・条件 |
|---|---|---|
| IN-01 | 開発要求原文 | 研究用ケースでは必須。原文・出所・要求版を保存 |
| IN-02 | AIの説明原文 | 三者照合では必須。未取得でも解析は可能だが説明照合は「説明未提供」 |
| IN-03 | 構造化要求・説明 | 自動照合時に必須。確認者・確認日時・原文位置を付ける |
| IN-04 | APKまたは解析JSON | いずれか必須。両方なら対応ハッシュを検証 |
| IN-05 | 実行設定・規則台帳 | 固定版を指定、または使用した既定版を記録 |
| IN-06 | 人手レビュー | 任意。自動判定と別ファイルで保持 |
| IN-07 | 正解表 | 評価時のみ。通常の照合処理は読まない |

APKと解析JSONを同時指定した場合、SHA-256相違は対応付けエラーとする。JSONのみでハッシュや由来がない場合は「未検証」として解析一覧を出せるが、検証済みケースとして研究評価へ組み入れない。パッケージ名一致だけで同一APKとはみなさない。

説明入力には `origin_type=initial_response / posthoc_explanation / revision_response`、対象artifact_id、回答日時（不明はnull）、保存原文のハッシュを持たせる。「提案」「実装済み」「今後の予定」「例示」を区別し、提案だけの文章を実装済みの断言として照合しない。

構造化データでは必須キー欠落、未知の列挙値、重複JSONキー、参照切れを入力エラーにする。任意メタデータの欠落は警告とし、未知・未取得・空集合を区別する。元のプロンプトやAI回答に秘密情報があり得るため、閲覧用の伏字版と原本を区別する。

## 6. 共通データ要件

| エンティティ | 必須の意味情報 |
|---|---|
| Case | case_id、実験区分、生成系列・生成条件、対象成果物、各入力の版とハッシュ |
| Artifact | artifact_id、APK SHA-256、package/version（取得可能時）、解析との対応確認状態 |
| Requirement | requirement_id、原文位置、対象domain、predicate、value、適用範囲、明示性、構造化確認情報 |
| Claim | claim_id、説明原文位置、domain、predicate、value、対象範囲、提案／実装済み等の発言種別、確実性、確認情報 |
| Evidence | evidence_id、domain、raw/normalized値、抽出方法、APK内所在、元JSON位置、stage_id、証拠種別 |
| Stage | stage_id、状態、予定した範囲、完了範囲、除外対象、エラー、ツール版 |
| Finding | finding_id、関係する各ID、判定軸、判定、rule_id/version、理由、確認事項、限界 |
| Review | finding_id、確認者、日時、人手判断、理由。自動判定は変更しない |

原文位置にはファイルと行範囲または文字オフセットを使用する。APK内所在はManifest要素、DEXクラス等、取得できた粒度で記録する。行番号やメソッドが取得できない場合は未取得とし、架空の位置を生成しない。人がソース確認で追加した証拠は `source=manual_oracle` として自動証拠から分離する。

要求と説明の関係は多対多で保持する。説明にない要求、要求にない説明、両者に対応しない構成も保持する。「要求がない」ことは、その構成が不必要である証明ではない。

## 8. 証拠と解析状態

各stageは `status=success / partial / failed / unsupported / not_run` と `coverage=complete_in_scope / partial / unknown` を別に持つ。正常終了と完全性を同一視しない。complete_in_scopeは、宣言した走査範囲の完了を意味し、アプリのすべての挙動を解析した意味ではない。

証拠種別は `manifest_declaration / embedded_string / sdk_signature / api_reference / config_value` 等とする。確率風の信頼度を根拠なく付けず、規則で証拠の性質を区別する。検出件数0と抽出不能は別の値で表す。

権限：Manifest内の要求宣言を対象に、条件付き宣言も条件とともに保存。付与済み・API実行済みとは説明しない。

URL：標準パーサーでHTTP(S) URLからホストを取り出す。ホスト比較は完全一致を基本とし、サブドメインを許す場合だけドット境界を含める。userinfo・ポート・末尾ドット・国際化ドメイン等の正規化規則とライブラリ版を固定する。単なる部分文字列一致は禁止。XML名前空間はその用途が確認できた出現のみ除外し、理由を残す。文書らしいURLを推測で除外しない。候補・ホスト・出現の件数を区別する。

SDK：sdk_id、署名条件、候補条件、ルール版、対応する難読化条件を台帳に持つ。単独文字列は候補、検証済み署名は同梱証拠として扱う。非検出から未知SDKの不存在を言わない。SDKカテゴリは固定台帳の分類であり、実際の用途の証明ではない。

## 9. 照合仕様

### 9.1 開発要求に対する判定

| 値 | 表示 | 条件 |
|---|---|---|
| mismatch | 要求との不一致 | 明示された制約への反証を証拠から確認 |
| conform_in_scope | 確認範囲で適合 | その制約を確認する範囲が完了し、規則上満たす |
| needs_review | 追加確認が必要 | 関連証拠はあるが抵触を確定できない |
| unspecified | 方針未指定 | 明示した制約がない |
| unknown | 判定不能 | 対応規則なし、解析失敗、必要な証拠不足 |
| out_of_scope | 対象外 | 静的構成の対象を超える要求 |

「通信しない」は「INTERNET権限を宣言しない」に自動変換しない。業務上の必要性・最小権限を機能名だけから確定しない。要求同士が明示的に矛盾する場合は入力の要確認とし、都合のよい方だけを採用しない。

### 9.2 AIの実装説明に対する判定

| 値 | 表示 | 条件 |
|---|---|---|
| supported_in_scope | 確認範囲で裏付けあり | 主張の範囲と一致する証拠がある |
| contradicted | 説明と証拠が矛盾 | 同じ対象・条件について、主張と両立しない事実がある |
| insufficient_evidence | 裏付け不足 | 主張に必要な証拠を得られない |
| out_of_scope | 対象外 | 実際の送信・保存の安全性など初版で確認できない |
| not_asserted | 実装済みの主張ではない | 提案・予定・例示のみで実装を断言していない |
| explanation_unavailable | 説明未提供 | 元の説明が保存されていない |

「反証が見つからない」と「正しい」を区別する。SDKの同梱証拠は「SDKが含まれる」を支持しても「SDKが実際に送信した」を支持しない。断定文・可能性表現・否定文と量化範囲を保持し、「含まれない可能性がある」を「含まれない」と読み替えない。複数条件を含む文は原文を保存した上で検証可能な主張へ分解する。

### 9.3 説明漏れ候補

構成単位で `covered / partially_covered / omission_candidate / ambiguous / not_evaluable` を保持する。説明の記載有無と説明の正誤は別軸である。説明が構成を否定していれば、通常は説明漏れではなく説明矛盾として扱う。

評価対象構成の粒度は実験前に固定する。初期案：権限は完全名または事前定義した意味カテゴリ、URLは正規化ホスト、SDKは固定sdk_id。意味カテゴリと包含規則は台帳に保存する。「外部サービスを利用する」のような総称を、特定の送信先や全SDKの完全な説明として扱わない。名称または対応する役割への言及を認める条件は、SDKごとに定義する。

主張抽出が失敗したときは原文に記載がないとは限らない。説明原文全体の構造化確認が完了している場合だけ omission_candidate を出す。説明未提供・回答切断・記載範囲不明なら not_evaluable。弱いSDKヒントのみの場合は、構成自体の不確かさも併記する。

### 9.4 初版で扱う規則例

| ID | 原文を構造化した条件 | 証拠 | 判定 |
|---|---|---|---|
| R-PERM-01 | 宣言権限を指定集合に限定 | 集合外の権限宣言 | 要求不一致 |
| C-PERM-01 | CAMERA権限を宣言した | 当該宣言 | 裏付けあり |
| C-PERM-02 | 位置情報権限を宣言していない | 当該宣言あり | 説明矛盾 |
| C-PERM-03 | 特定の宣言がある | Manifest全対象走査完了、その宣言なし | 宣言の存在に限り説明矛盾 |
| R-URL-01 | 通信先を許可ホストに限定 | 許可外のURL文字列 | 追加確認。実通信先違反を確定しない |
| C-URL-01 | 特定URL文字列が含まれる | 同じ候補あり | 文字列の存在について裏付けあり |
| C-SDK-01 | SDK-Aを組み込んでいない | SDK-Aの検証済み同梱署名 | 説明矛盾 |
| C-SDK-02 | SDK-Aを組み込んだ | 非検出のみ | 原則、裏付け不足。不存在と断定しない |
| O-SDK-01 | 評価対象SDKへの対応説明なし | 確かな同梱証拠、原文確認完了 | 説明漏れ候補 |
| B-BEH-01 | 外部通信は一切発生しない | URL・INTERNET権限のみ | 実挙動は対象外。関連構成を確認事項に提示 |

規則台帳は適用条件、必要証拠、反証条件、負の判定に必要な範囲、出力文、限界、検証ケースを持つ。数値スコアで三者を一つの安全判定へ集約しない。

## 10. 出力と説明要件

| 出力 | 内容 |
|---|---|
| result.json | 入力識別、正規化構成、全証拠、三者の対応、判定、規則、失敗 |
| report.md | 日本語の構成説明と確認事項、原文・証拠への参照 |
| run.json | 入力ハッシュ、使用ツール・ルール・台帳版、実行条件、時間 |
| findings.csv | 評価用の1判定1行。複数IDはJSON配列文字列 |
| reviews.json | 任意の人手確認。自動結果とは別 |
| raw_inputs/ | 要求・AI回答・解析JSONの保存コピー。APKは保管参照でも可 |

レポートは、対象と解析範囲 → 構成の概要 → 要求不一致 → 説明矛盾 → 説明漏れ候補 → 方針未指定・追加確認・判定不能 → 証拠詳細、の順に提示する。不一致・矛盾が0件でも未確認範囲を同じ要約内に表示する。総合安全スコアは設けない。

各項目は「開発要求／AIの説明／確認した事実／判定と理由／根拠の場所／次に確認すること／わからないこと」を持つ。専門語には短い説明を付け、詳細なクラス名等は根拠欄へ分ける。図は任意とし、未解析の因果関係を矢印で追加しない。単に根拠IDが存在するだけで説明の妥当性を認定しない。

例（仮想ケース）：

> 要求：位置情報に関する指定なし。  
> AIの説明：「位置情報の権限は追加していません」。  
> 事実：ManifestにACCESS_FINE_LOCATIONの宣言を確認。  
> 判定：要求は方針未指定。AIの説明は宣言について矛盾。  
> 確認事項：この権限宣言を採用するか、AIへ変更を依頼するか確認する。  
> 限界：この結果だけでは、位置情報の取得処理や実際の取得・送信は判断できない。

## 11. 非機能要件

| ID | 要件 |
|---|---|
| NF-01 再現性 | APK・原文・構造化入力・解析JSONのハッシュ、ツール・アダプター・規則・台帳の版を記録。LLM使用時はモデル名・実施日・設定・全文を保存し、完全再現は保証しない |
| NF-02 非実行 | APKのアプリコードを実行しない。抽出URLへ接続しない。初版は外部LLM/APIへの送信を必要としない |
| NF-03 ファイル保護 | 作業先を実行ごとに分離。入力と過去結果を上書きしない。展開先逸脱、外部実体参照、シェル文字列連結を防ぐ |
| NF-04 資源制御 | APKサイズ、展開量、メンバー数、ツール時間の上限を設定・記録。初期値は現行環境の試行後に固定。超過時は影響範囲をpartialにする |
| NF-05 部分失敗 | 失敗領域を適合にせず、他領域の確かな反証は残す。抽出失敗を構成削除と扱わない |
| NF-06 可搬性 | UTF-8、日本語パスを受理。文字列をJSON・Markdown等で適切にエスケープし、CSVの数式実行を防ぐ |
| NF-07 保守性 | 抽出・正規化・要求照合・説明照合・説明対応・出力を分離し、規則を版管理 |
| NF-08 性能 | 保証時間を現段階で置かず、APK規模・経過時間・処理量を測定して報告 |
| NF-09 機密性 | 不要な原文・URL全文を通常ログに複製しない。共有レポートの伏字を原本の改変と混同しない |

代表エラー：INVALID_INPUT、UNSUPPORTED_SCHEMA、ARTIFACT_MISMATCH、BROKEN_REFERENCE、PARTIAL_EXTRACTION、TOOL_TIMEOUT、MISSING_EXPLANATION、UNSUPPORTED_PREDICATE、OUTPUT_EXISTS。エラー・候補・不一致の有無を混同しない。処理成功でも不一致はあり得る。

## 13. 研究評価のための要件

正解は二層で用意する。(A)ソース・設定・ビルド情報から人手で確認した実装上の構成、(B)自動抽出した証拠だけから判断できる範囲。Aは抽出漏れを、Bは照合・説明の誤りを評価するために使う。ソース上の実装確認を、実行観測と呼ばない。

正解表には対象単位、期待する判定、根拠、確認者、日時、意見不一致の解決記録、開発用／評価用の区分を持つ。可能な範囲で別確認者による検証を行い、一人のみの場合は限界として報告する。LLMの採点だけを正解にしない。

| 評価 | 指標・集計上の要件 |
|---|---|
| 抽出 | 権限・URL候補・SDKの対象範囲別適合率・再現率。URL候補検出と実通信を分ける |
| 矛盾・不一致検出 | 判定単位別TP/FP/FN等。unknownは真陰性にしない。未判定の真の問題も見逃し内訳として示す |
| 説明対応 | 説明漏れ候補の適合率・再現率、部分対応・曖昧・未評価件数 |
| 根拠 | 主張を支持しない証拠への誤対応件数、参照切れ、根拠のない断定件数 |
| 判断範囲 | 判定可能率・対象外率・判定不能率。精度と併記 |
| 実行 | ビルド失敗、解析失敗、処理時間、対象ごとの失敗理由 |

分母はAPK数、要求数、説明主張数、構成数、判定数を区別する。原文一文から分解した主張を独立アプリのように数えない。重複出現を独立構成として水増ししない。分母0は算出不能とし0%へ置き換えない。

比較は二種類を分離する。第一に同じ情報を使う一覧表示と三者対応表示の比較で、確認対象のカバー率と誤提示を評価する。これは理解向上の評価ではない。第二に、LLM説明を導入する場合のみ、同じモデル・同じ原文と証拠・同じ出力対象を使って規則の有無を比較する。ソースを渡す条件との比較は入力情報量が違うため別実験とする。

実験記録は自然生成／人工的検証ケースを区別する。AI説明に矛盾が0件でも報告する。修正後APKや追加説明を扱う場合は独立生成と分ける。研究者が後から作った方針は、元の生成指示違反の判定に使わない。

## 14. 実装段階と完成判定

| 段階 | 作るもの | 完了条件 |
|---|---|---|
| M0 棚卸し | 現行コード・解析JSON・保存済みAI回答の確認 | 入出力対応表、実際に取れる証拠、未対応範囲が確定 |
| M1 最小照合 | P0、手動構造化入力、固定規則、テンプレート説明 | 旅行記録アプリ一件の入力・証拠・レポート・正解表が揃う |
| M2 研究評価版 | P1、受入ケース、基準表示、評価出力 | 固定した規則で受入条件を満たし、未使用ケースを評価できる |
| M3 条件付き拡張 | P2から必要なもののみ | 追加の受入条件と評価を行い、旧結果との差を管理 |

M1ではGUI、自由文の完全自動解析、LLM説明生成、HTTP実効設定の全解釈、差分解析を必須にしない。既存解析器の全面的な作り直しは前提にしない。証拠がない領域をunknownで返す実装と、研究対象機能を実現できたことは区別する。

## 15. 旧仕様からの変更と移行

| 項目 | v1.0 | 本書v2.0 |
|---|---|---|
| 中心 | 開発意図とAPKの二者照合 | 開発要求・AI実装説明・APKの三者照合 |
| 要求入力 | 構造化意図が常に必要 | 原文を保存。制約未指定でも構成と説明を確認 |
| 判定 | 不一致・候補・適合等を中心に提示 | 要求判定、説明判定、説明対応を別軸にする |
| 追加機能 | 修正前後差分が研究用完成版で必須 | 原則拡張。説明主張・説明漏れ候補・三者対応を優先 |
| HTTP設定 | 研究用完成版で必須 | 追加の対応表と検証が必要な拡張 |
| SDK | 条件付き拡張 | 固定した既知SDK範囲を最小対象に含める。未成立なら題目・対象を改訂 |

v1入力や既存JSONは明示的なアダプターで変換し、元データと変換版を保存する。旧判定を新しい説明矛盾に機械的に置き換えない。API・ホスト正規化などの旧詳細設計は、適合する範囲で再利用できるが、本書と競合する必須範囲・判定意味は本書を優先する。

## 16. 着手時に確定する事項

1. 旅行記録アプリの生成時回答全文、ソース、ビルド済みAPKが保存されているか。
2. 現行解析器の起動方法、出力schema、ツール版、段階別エラーの取得可否。
3. 権限・URL・SDKそれぞれの証拠位置と、SDK署名台帳の有無。
4. 最初に評価するSDK集合、説明対応の意味カテゴリと粒度。
5. 負の主張を判定するための抽出完了条件。
6. 初版の実行環境と資源上限。

これらは実装接続に必要な未確定事項であり、現段階で機能実装済みという意味ではない。最初の開発成果物は、旅行記録アプリ一件についての「要求表・説明主張表・証拠表・照合レポート・独立正解表」の一式とする。
